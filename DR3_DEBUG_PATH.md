# Isolated DR3 probe

> The new persistent debugger session is documented in `KI_CR3_SESSION.md`. The commands below remain isolated probes, not proof that persistent sessions are safe. Do not run them concurrently with a persistent session. Persistent activation disables Host/Guest unload until reboot or snapshot restore.

This experimental path reserves DR3 for the SVM host. It does not hook `KiDispatchException`. The Guest retains three functional hardware address-breakpoint slots (DR0–DR2); intercepted Guest DR3/DR7 reads and writes return per-vCPU shadow state. Guest DR3 breakpoints are intentionally not functional.

`VIRTUAL_PROCESSOR_DATA` stores private target, original DR3/DR7, shadow state and hit count **after** the fixed Host stack, VMCBs and host state area. The `HostStackLayout` size, the stack-base pointer and its offsets are unchanged. The assembly uses the existing `Self` pointer before VMRUN and preserves caller-saved GPRs; VMEXIT restores Host debug registers before processing events. On unload the Guest-visible DR3/DR7 are restored.

## VM snapshot test only

1. Restore a known-good snapshot following the previous blue screen. Replace **all three** binaries together from this build; never mix the earlier crashing Host driver with the new Guest driver.
2. Enable a kernel dump and ensure there is a recovery snapshot. Confirm the SVM driver starts and stops without the Guest driver before testing the probe.
3. Load the Guest driver and run `LMvtdriverGuestControl.exe --dr3-smoke` once. Expected: `PASS status=00000000 step=7 ... hits=N:N+1:N+1`.
4. On any failure, especially a crash, do not rerun the command. Preserve bugcheck parameters and a crash dump for analysis, then restore the VM snapshot.

Passing this one-CPU synthetic test does not validate simultaneous Guest hardware breakpoints, DR7.GD edge cases, all-CPU arming, nested SVM or real Ki exception dispatch. It must not be used for normal debugging until those cases are addressed.
## Per-CPU sequential probe

After the one-CPU test passes in a recoverable VM snapshot, rebuild the Guest control EXE and run `LMvtdriverGuestControl.exe --dr3-all-cpus-smoke` once. It pins the calling thread to each active processor in sequence and reuses the one-CPU arm/hit/disarm IOCTL. Expected: one `guest dr3-smoke: PASS` per CPU and `guest dr3-all-cpus: PASS tested=N expected=N`. Stop at the first failure; preserve the dump if the VM crashes.

This command does not test concurrent breakpoints or native Guest #DB delivery (including DR0-DR2), and does not install a breakpoint on KiDispatchException.

## Native DR0-DR2 smoke

After rebuilding only the VT project's Guest Control executable, run `LMvtdriverGuestControl.exe --native-dr-smoke` in the recoverable VM. The test creates a suspended user thread, assigns one execute breakpoint at a time to DR0, DR1, and DR2, catches `EXCEPTION_SINGLE_STEP` with a vectored handler, and removes the slot before moving to the next one. Expected: three per-slot PASS lines and a final `guest native-dr-smoke: PASS`. A failure or crash means native Guest hardware-breakpoint behavior is not yet safe; do not proceed to Ki integration.

## Native/private coexistence smoke

After rebuilding the Guest driver and Guest Control executable together (the Host driver is unchanged), run `LMvtdriverGuestControl.exe --dr-coexist-smoke` once in a recoverable VM. The test keeps a private DR3 armed in the Guest driver, triggers an independent Guest DR0 execution breakpoint on the same vCPU, then triggers the private DR3 target and verifies counts: DR0 exactly once, private DR3 exactly once, and no additional hit after disarm. Expected: `PASS status=00000000 step=6 dr0={hits=1 unexpected=0 ...} dr3=N:N:N+1:N+1:N+1`. Stop on failure or crash and restore the snapshot.

## One-shot Ki entry probe

Restore a VM snapshot and replace the Host driver, Guest driver, and Guest Control executable together from the same Debug/x64 build. Confirm the existing `--dr3-smoke` still passes, then run `LMvtdriverGuestControl.exe --ki-dr3-probe` once. The Guest resolves and verifies the KiDispatchException entry before arming one CPU; the Host records the first private DR3 hit and disables that slot immediately. The control program raises a handled user-mode exception on the same CPU; the Guest waits up to three seconds and checks the recorded RIP, DR6.B3, and CR3, verifies DR3 was auto-disarmed, and explicitly disarms it again before returning. Expected: `guest ki-dr3-probe: PASS status=00000000 step=4 ... hit=N:N+1 rip=<ki> dr6=<B3 set> cr3=<nonzero> caught=1 wait=0 win32=0`. Stop on any failure or bugcheck and preserve the dump; do not repeat before restoring the VM snapshot.

The first Ki entry hit can belong to another exception on the same CPU; this probe cannot attribute it to the synthetic exception. It neither pauses exception dispatch nor forwards a real debugger event or register edits, and it does not validate nested SVM or all-CPU interception.

## Hardware-exception diagnostic

If the software-exception `--ki-dr3-probe` prints `step=2 hit=N:N` without crashing, do not infer that the Ki breakpoint was cleared. In a recoverable VM snapshot replace Host, Guest, and control executable together, then run `LMvtdriverGuestControl.exe --ki-dr3-probe-ud2` once. This variant raises a handled illegal-instruction exception on the pinned user thread. The diagnostic prints `armed-after` (private DR3 target after triggering) and `dr7-after` (the vCPU VMCB DR7 snapshot before cleanup). If `hit` does not increase while `armed-after` equals `ki` and `dr7-after` includes bit 6, the private breakpoint was still armed but that Ki entry was not observed. If `hit` increases, the first Ki entry was captured; it is not necessarily attributable to the synthetic exception. Stop after any failure or bugcheck and retain the full log/dump.
## Ki entry register snapshot

`--ki-dr3-probe-ud2` now queries the first one-shot Ki #DB hit on the pinned processor after confirming that the hit count increased. On PASS it prints `guest ki-dr3-snapshot` with the processor group/number and the Ki-entry RCX, RDX, R8, R9, RSP, RFLAGS, RAX and RBP values recorded in VMEXIT. A failed or absent hit does not produce a snapshot line. Replace the Host driver, Guest driver and Guest Control executable together from one build and run this command once in a recoverable VM snapshot; stop on a failure or bugcheck and preserve the log/dump.

These are raw register values at the first observed Ki entry, not decoded exception arguments or evidence that the hit belongs to the synthetic UD2. The probe does not wait in VMEXIT for R3, emit a debugger event, or modify guest registers.
## Stack-relative pointer diagnostics

On a successful `--ki-dr3-probe-ud2`, the control program additionally prints `guest ki-dr3-stack-candidates`. It reports offsets of the VMEXIT-captured RCX, RDX, R8, R9, RAX and RBP values from VMEXIT-captured RSP when a value is in `[RSP, RSP + 0x1000)`; `outside` means it is not in that bounded range. This is address arithmetic only: it does not read stack memory, verify a trap frame or identify exception parameters. Do not dereference the saved RSP later in the Guest driver: by then the exception may have returned and the original stack contents may have changed or become inaccessible. A reliable stack snapshot would have to be captured at the hit, with a safe and bounded Guest-virtual-to-Host mapping and explicit read-failure handling, before continuing Guest execution.
## One-shot Ki DR3 redirect smoke

On a recoverable VM snapshot, deploy Host `LMvtdriver.sys`, Guest `LMvtdriverGuest.sys`, and `LMvtdriverGuestControl.exe` from the same Debug/x64 build. Run `--ki-dr3-redirect-smoke` once. It arms a single processor's DR3 breakpoint at KiDispatchException, passes the address of the Guest driver's nonpaged, executable `LmvGuestKiDr3RedirectStub` through the shared command, and on the first matching #DB VMEXIT disarms DR3 and replaces Guest RIP. The stub increments a counter and jumps to the original Ki entry without waiting or changing the exception frames. `PASS ... calls=N:N+1` and a caught UD2 show that one selected entry made a round trip; it does not establish exception ownership, correct debugger-event delivery, or register editing. The raw DR3 probe `--ki-dr3-probe-ud2` remains unchanged. Stop on any failure, hang, or bugcheck and preserve the VM dump/log. Do not deploy this as a persistent hook: the smoke uses a single Guest-driver-global return target and does not protect against concurrent redirections or unloading during an active redirect.
## One-shot Ki read-only inspection

In a recoverable VM snapshot, deploy the Guest driver and Guest Control executable from the same Debug/x64 build along with the compatible Host driver, then run `--ki-dr3-inspect-smoke` only once. Unlike `--ki-dr3-redirect-smoke`, this variant redirects to a separate Guest assembly stub that preserves the entry general-purpose registers and flags, passes the original KiDispatchException RCX/RDX/R8/R9 and the fifth stack argument to a read-only Guest helper, then jumps back to the original Ki entry. The helper accepts only a user-mode first-chance exception in the smoke executable's process, checks IRQL before calling `MmCopyMemory`, and copies only the fixed prefix of the `EXCEPTION_RECORD`; it never reads or changes the trap/exception frames. Expect `guest ki-dr3-probe: PASS`, `guest ki-dr3-redirect: PASS ... calls=N:N+1`, and `guest ki-dr3-inspect: PASS copy-status=00000000 reason=7 ... raw-code=10000002 ... user-code=c000001d ... first=1`. The observed raw `0x10000002` matches the Windows kit `KI_EXCEPTION_INVALID_OP` marker on supported architecture headers; do not rewrite the Guest record or assume this internal value on every Windows build. The control program verifies that the raw record address at the Ki entry equals the user-mode SEH address caught for this UD2 before declaring PASS. The R3 control program additionally requires the captured PID and TID to match the triggering R3 thread. A first Ki hit from another context can instead produce FAIL with a reason: 1=high IRQL, 2=not user mode, 3=not first chance, 4=other process, 5=invalid record pointer, 6=copy failure. This is a smoke-only PID filter, not an attached-debuggee event pipeline. It does not wait, modify contexts, or prove that nested SVM can observe every exception. Stop on failure/hang/bugcheck and preserve the VM dump and log.

## One-shot Ki read-only frame comparison

After the previous inspection passes, deploy the matching Guest driver and Guest Control executable together and run `--ki-dr3-frame-smoke` once in a recoverable VM snapshot. This separate mode reads bounded copies of the Ki-entry `KTRAP_FRAME` and `KEXCEPTION_FRAME` using `MmCopyMemory` at IRQL no higher than APC_LEVEL, snapshots volatile and nonvolatile GPRs, and compares trap-frame RIP/RSP/RBP with the R3 SEH `CONTEXT` and the exception address. RBP comes from the trap frame: the WDK marks exception-frame RBP as not always saved, and the initial smoke observed a zero there while user-mode RBP was nonzero. It prints both sides' GPRs and RFLAGS for diagnosis; only RIP/RSP/RBP equality is required because exception dispatch can alter other values. Expect `guest ki-dr3-frame: PASS status=00000000 reason=12`, but treat the complete register logs as observations, not a guarantee that all frame fields are valid across Windows builds. Frame failures use reason 8=bad frame pointer, 9=trap copy failed, 10=exception copy failed, or 11=unexpected user-frame RIP/RSP/CS; stop on failure and preserve the log and dump. No frame writes, debugger events, waits, or persistent hook are introduced. The frame layout is tied to the WDK and must be checked against the running Windows build before attempting context writeback.

## One-shot Ki Guest event round trip

Run `--ki-dr3-event-smoke` once in a recoverable VM snapshot with the matching Guest driver and Guest Control executable. This mode adds a separate, single-slot event and a dedicated second device handle. The one-shot Ki Guest stub only waits when the exception belongs to the smoke process, it is first chance, the frame copy succeeded, the IRQL is PASSIVE_LEVEL and interrupts are enabled. It publishes the copied frame, sleeps in Guest kernel mode for at most two seconds, then resumes the original Ki entry after the controller issues a matching-sequence continue. The R3 broker waits on its own thread and device handle so that the triggering R3 thread can remain blocked. Expect `guest ki-dr3-event: PASS status=00000000 ... received=1 continued=1`; on timeout, cancel, wrong PID, or sequence mismatch, it fails without changing the exception frame. The broker is restricted to the smoke controller process; this is **not** an attached-process debugger pipeline, does not write registers or wait in Host VMEXIT, and should not be run repeatedly after a bugcheck or unexpected hang. Detach, long-lived hooks, multi-threaded delivery, real debugger ownership and unload synchronization remain for later stages.

The broker now also sends an invalid sequence and attempts a second delivery before the valid continue; both must be rejected (`wrong-sequence-rejected=1 duplicate-rejected=1`). Only the handle that claimed the event may continue it. Closing that handle wakes the original thread and cancels the wait. The existing Host private DR3 interception is still **one-shot on one CPU**, so this test cannot prove coverage for an attached multi-threaded target. Do not route debugger exception handling to these smoke IOCTLs until a separately validated all-CPU, rearmable interception path and per-thread event lifetime are available.

## Sequential per-CPU Ki event rearm smoke

After the single-CPU event smoke passes, deploy the updated Guest Control executable with the matching Host and Guest drivers in a recoverable VM snapshot. Run `--ki-dr3-all-cpus-event-smoke` once. It pins the initiating R3 thread to each active processor in turn and performs two complete one-shot Ki DR3 event round trips per processor. Each round checks that the Host disarmed DR3, that the Guest event was received exactly once with matching PID/TID/frame, and that an invalid sequence and duplicate delivery are rejected before valid continue. Expect `guest ki-dr3-all-cpus-event: PASS tested=8 expected=8 rounds=2 mode=serial-one-shot` on a four-CPU system. Stop at the first FAIL and preserve the complete log and VM dump. This deliberately uses serial one-shot rearming; it does **not** install an all-CPU persistent hook or support concurrent debugger events. Global Guest stub return state, live-Guest-driver unload, and per-thread event lifetime must be redesigned before deploying a persistent Ki interceptor.

## Independent Guest event waits (not persistent interception)

The Guest event transport now reserves one nonpaged wait slot per captured exception (up to 16). Each slot owns its own completion event, snapshot and sequence; the first unclaimed pending event is returned to one consumer handle, and only that handle can continue it. A full set of slots rejects a new wait without blocking, and a timed-out, continued, or cancelled waiter returns its own slot to the pool. Owner/consumer handle cleanup cancels outstanding waits. The previous serial Ki smoke still exercises only one slot per round; it does not exercise simultaneous Ki interceptions. The read-only inspection result, return RIP, Host interception and active probe owner remain global/single-shot. Do **not** install a persistent all-CPU breakpoint, allow Guest driver unload while a redirected stub can run, or route the debugger through this transport until those remaining lifetimes and concurrent paths are implemented and validated separately.

The event waiter captures the owner-session generation before sleeping, and rejects a wake from a later session even when that session belongs to the same process. The R3 event smoke also attempts to continue the claimed sequence through a second device handle; expect `foreign-handle-rejected=1`. These checks protect the existing one-shot transport but do not test simultaneous intercepted exceptions. Deploy matching Guest driver and control executable together and run the smoke in a recoverable VM snapshot.

The event-wait IOCTL maps an empty-queue wait timeout to a failing status (`STATUS_IO_TIMEOUT`). It also returns failing statuses when every pending event is already claimed or the queue is empty. Returning informational `STATUS_TIMEOUT` previously made `DeviceIoControl` report success with zero output bytes, causing the duplicate-delivery smoke to fail even though the event was not delivered twice.

## Concurrent Guest queue smoke (no Host hook)

Deploy matching Guest driver and Guest Control executable in a recoverable VM snapshot and run `LMvtdriverGuestControl.exe --ki-queue-concurrency-smoke`. A diagnostic-only session starts two user threads that each enter the Guest event wait path through a synthetic producer IOCTL. Two independent handles claim both events before either is continued, and a cross-handle continue is rejected before each owner continues its own event. Expect `guest ki-queue-concurrency: PASS delivered=2 cross-rejected=1 continued=1 producers=1 ... mode=synthetic-no-host-hook`. The synthetic exception code is `E0424D56`; there is no real exception frame, Ki interception, DR3 arm, or debugger attachment. If it hangs, fails, or bugchecks, restore the snapshot and retain the complete log/dump. This test covers concurrent Guest queue ownership only; the Host intercept and stub lifetime must still be redesigned before genuine concurrent Ki events are safe.

Run `LMvtdriverGuestControl.exe --ki-queue-cancel-smoke` separately to test consumer-handle cleanup. The control claims one synthetic event, closes its consumer handle without continuing, and checks that the producer is cancelled before its two-second wait expires. Expect `guest ki-queue-cancel: PASS received=1 cancelled=1 ended=1 ... mode=synthetic-no-host-hook`. This does not arm DR3 or intercept KiDispatchException. Do not unload the Guest driver while any real Ki redirect could still be active; the current global return RIP and unload lifetime are not safe for persistent or parallel redirects.

## One-shot handled UD2 experiment

The new `ki-dr3-handled-smoke` mode is restricted to a single first-chance user UD2 event on the pinned CPU. The consumer must claim the event, set RIP to the verified UD2 address plus two bytes, and then continue with the handled disposition. The Guest stub restores the original registers and flags and returns to KiDispatchException's caller instead of dispatching the UD2 to user SEH. A premature handled continue, a synthetic event, or an unrecognized instruction must not be marked handled. This does not implement process attachment, persistent interception, arbitrary RIP updates, or a general debugger context API.

This path is compiled but **not run**. A previous version bugchecked without an available dump. Test only in a recoverable VM snapshot with matching binaries and kernel debugging or crash dumps enabled; stop after any hang, mismatch, or bugcheck, and preserve the dump. Run `--ki-queue-concurrency-smoke` first, then `--ki-dr3-event-smoke`, before considering `--ki-dr3-handled-smoke`.

## Experimental one-shot register writeback

The RAX smoke now rejects a wrong sequence and a second consumer handle before submitting the valid write, checks the returned IOCTL size, and compares the Guest capture with the user SEH context. The synthetic concurrency smoke rejects RAX writes to synthetic events before continuing both producers. These are protocol checks only; neither test makes the Ki interception persistent or marks an exception handled.

`--ki-dr3-rax-smoke` arms one VP for one real Ki entry and uses a separate, sequence- and consumer-bound IOCTL to submit an RAX value while the original exception thread waits in Guest code. On successful continue, only the trapped thread's `KTRAP_FRAME.Rax` is updated; the Guest stub still jumps to the original Ki entry, allowing Windows to process the UD2 normally. This is not a handled-exception disposition, RIP rewrite, general SET_CONTEXT implementation, or debugger backend. The write IOCTL is disabled outside this exact one-shot probe mode and rejects synthetic queue events. Because a prior build bugchecked and its dump was unavailable, do **not** run this new kernel smoke until the prior bugcheck has been diagnosed and a recoverable VM snapshot and matching Host/Guest/control binaries are available. A successful build is not evidence that the context writeback is safe on the target Windows build.
